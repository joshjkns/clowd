# Relationships

A relationship is one line that says how a service uses something else:

```clowd
api connects to db
api reads and writes uploads
worker reads jobs
api sends to jobs
```

Each one generates the network path, the permissions, and environment
variables in the service, so your code finds what it needs without knowing
which cloud it runs on. Most of the boilerplate in hand-written Terraform
lives here.

## Verbs

There are exactly five, and one target per line.

| Verb | Meaning | Targets |
|---|---|---|
| `connects to` | network path, credentials and connection variables | `database`, `service` |
| `reads` | read-only access; on a queue, consume | `bucket`, `queue` |
| `writes` | write-only access | `bucket` |
| `reads and writes` | read and write access | `bucket` |
| `sends to` | publish | `queue` |

Only services start relationships. Load balancers route with `send`, and
databases, buckets and queues are passive.

## One phrasing

Each relationship has one way to say it. The common wrong guesses are errors
that name the right verb, and the line is still read with that verb, so the
rest of the file checks normally:

```sh
error: unknown relationship `links to`
 --> app.clowd:4:5
  |
4 | api links to db
  |     ^^^^^^^^
  = help: did you mean `connects to`?
```

The same goes for a verb that doesn't fit its target. To publish to a queue
you say `sends to`, never `writes`:

```sh
error: `writes` doesn't apply to a queue
  = help: to publish to a queue, write `api sends to jobs`
```

## Environment variables

A relationship sets variables in the service named after the target:
`<NAME>` is the target's name in upper case, with `-` as `_` (`db` becomes
`DB`, `user-files` becomes `USER_FILES`). They're the same on every cloud.

| Relationship | Variables |
|---|---|
| `connects to` a database | `<NAME>_HOST`, `<NAME>_PORT`, `<NAME>_NAME`, `<NAME>_USER`, `<NAME>_PASSWORD` |
| any verb to a bucket | `<NAME>_BUCKET` |
| `reads` or `sends to` a queue | `<NAME>_QUEUE_URL` |

`<NAME>_NAME` is the database created inside the instance: the resource's
name in lower case with `-` as `_`, ending in `_db` (`db` becomes `db_db`,
`users` becomes `users_db`), so it's never a word the engine reserves.

On GCP, `<NAME>_QUEUE_URL` is the Pub/Sub topic's path for a service that
sends and the subscription's path for one that reads. A service that does
both gets the subscription in `<NAME>_QUEUE_URL` and the topic in
`<NAME>_TOPIC`.

The password is a secret. It's generated at deploy time and kept in the
cloud's secret store; it's never written in your configuration or in
OpenTofu's state, and it's handed to the service when it starts. If a service sets an `env` with the same name, its
own value wins, with a warning.

## What it builds on AWS

For `api connects to db`:

- an ingress rule on the database's security group, from the service's
- an IAM policy on the service's execution role to read the database's
  generated password from Secrets Manager
- the five variables in the task definition, with `DB_PASSWORD` injected as a
  secret

For `api reads and writes uploads`, an IAM policy on the task role that
allows listing that bucket and getting, putting and deleting its objects,
plus `UPLOADS_BUCKET`.

## What it builds on GCP

Every service runs as its own service account, and relationships grant that
account access. For `api connects to db`:

- Direct VPC egress from the Cloud Run service into the network, where the
  Cloud SQL instance has only a private address
- access for the service account to the Secret Manager secret holding the
  password
- the five variables on the container, with `DB_PASSWORD` read from the
  secret

For `api reads and writes uploads`, the `storage.objectUser` role on that
bucket, plus `UPLOADS_BUCKET`; `reads` alone gives `storage.objectViewer`.
Cloud Storage has no role that writes without reading, so `writes` can read
too, and `clowd check` shows it as ⚠.

A service that `reads` a queue pulls from its subscription between requests,
so its CPU stays allocated. It should scale from at least 1: Cloud Run only
starts instances for requests, and `clowd check` warns when one can scale to
zero.
